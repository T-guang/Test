# V2.3.9.1.1 基线一致性修正调查

## 范围与结论

本次只修正 Editor-only 基线采集来源与快照字段。未修改 `CircuitValidationService`、任何 Validation Helper、`CircuitStateAnalyzer`、`LocalInspectorPanel`、模板 JSON、`Demo.unity` 或业务报告逻辑。

结论：

1. 旧 `ValidationRuleSnapshots.json` 的 Severity 来自 `ArchitectureBaselineSnapshotWriter.CreateRuleCatalog()` 中的手写字典，不是生产规则唯一来源；
2. `NEUTRAL_PE_MISUSE` 的生产 Severity 是 `Warning`；
3. `REVERSING_INTERLOCK_MISSING` 的生产 Severity 是 `Warning`；
4. 正常模板 Inspector 快照中出现的 `errorCount = 2` 是旧快照工具的中文关键词误判，并非 `CircuitValidationService` 返回了 Error；
5. 新采集方案改为从生产 `CircuitValidationIssue` 发射点读取 `CircuitValidationSeverity` / `CircuitValidationCategory`，并单独保存 Inspector 的实际管线来源计数。

## Severity 唯一来源

运行时唯一可交付的 Severity 值是 `CircuitValidationIssue.Severity`。其生产发射点由 `CircuitValidationService` 与各 Helper 调用 `AddIssue` / `CreateIssue` 时传入的 `CircuitValidationSeverity` 和 `CircuitValidationCategory` 决定。

`ArchitectureBaselineSnapshotWriter` 不再维护 `RuleId -> expectedSeverity` 手写表。生成时会扫描：

`Assets/Scripts/Core/Validation/**/*.cs`

并记录每条规则的：

- `severities`：生产发射点实际出现的枚举值；
- `categories`：同一发射点的 `CircuitValidationCategory`；
- `sourceLocations`：相对项目路径与行号。

对 `COIL_VOLTAGE_MISMATCH`，生产逻辑会按失配方向经过 `AddCoilMismatchIssue(..., severity, ...)` 传入 `Error` 或 `Warning`；基线会记录两个实际枚举值，而不是写入自定义文字契约。对 `COMPLEX_LOOP_OR_UNSUPPORTED_TOPOLOGY`，规则 ID 由 `TopologyTraversalLimits.ComplexTopologyRuleId` 声明，Severity/Category 由 `CircuitValidationService.AddComplexTopologyIssue` 发射点读取。

## 旧值与新值

| RuleId | 旧基线值 | 生产来源的新值 | 证据 |
|---|---:|---|---|
| `NEUTRAL_PE_MISUSE` | `Error` | `Warning / GroundSafety` | `PowerPotentialValidationHelper.cs:113-117`；`PowerSafetyValidationTests.cs:119-120` |
| `REVERSING_INTERLOCK_MISSING` | `Error` | `Warning / Interlock` | `ProtectionBypassValidationHelper.cs:185-188`；`ProtectionBypassValidationTests.cs:177-178` |
| `COIL_VOLTAGE_MISMATCH` | `ErrorOrWarningByMismatchDirection`（手写文字） | `Error`、`Warning` / `PowerSafety` | `PowerPotentialValidationHelper.cs:162-175`、`189-193` |
| `COMPLEX_LOOP_OR_UNSUPPORTED_TOPOLOGY` | `Warning`（手写） | `Warning / General` | `CircuitValidationService.cs:886-894`；RuleId 常量位于 `TopologyTraversalLimits.cs:12` |

其余 12 条规则也会在新版 JSON 中由同一生产扫描器记录，不再依赖 `ArchitectureBaselineSnapshotWriter` 的手写 Severity 常量。

## Inspector `errorCount` 与空 Validation 的来源分析

已生成的正常家庭模板快照中存在如下现象：

- `TemplateStaticSnapshots.validationIssues = []`；
- `validation errorCount = 0`；
- `InspectorReportSnapshots.check.errorCount = 2`。

这不是 Validation 与 Inspector 的业务结论冲突。旧基线工具在 `CaptureInspectorReport` 中执行了以下二次推断：

1. `InferSeverity(title, body)`：只要文本包含“错误”就将 block 标为 `Error`；
2. `snapshot.errorCount = blocks.Count(block => block.severity == "Error")`。

正常检查文本中包含“当前未检测到……错误”“未发现严重接线错误”等否定句，仍包含“错误”字样，因此被工具误计为 Error。此字段不是 `LocalInspectorPanel`、Analyzer、Validation 或参数估算的真实 ErrorCount。

### 真实检查入口的来源

`LocalInspectorPanel.CheckCurrentCircuit()` 有两条生产路径：

| 场景 | 实际检查来源 | 代码证据 |
|---|---|---|
| 工业电路 | `IndustrialCircuitRuleAnalyzer.TryAnalyze(...)` 的 `CircuitAnalysisResult.ErrorCount / WarningCount` | `LocalInspectorPanel.cs:418-436` |
| 家庭/非工业电路 | `CircuitRuleChecker.Check()`，再经过 `FilterCheckPanelFalsePositives(...)` | `LocalInspectorPanel.cs:459-472`、`2385-2440` |
| 新 Validation 规则摘要 | `PrependCircuitValidationSummary()` 内的 `CircuitValidationService.Validate(...)` | `LocalInspectorPanel.cs:1048-1139` |
| 参数估算 | `PrependParameterEstimationSummary()` 与工业参数估算摘要 | `LocalInspectorPanel.cs:1048-1160` |
| Analyzer 状态 | `AnalyzeCircuitState()` 结果用于运行态和报告摘要 | `LocalInspectorPanel.cs:431-438`、`462-473` |

参数估算和 Analyzer 状态可以出现在报告 block 中，但不是旧 `errorCount = 2` 的来源；该数值仅来自基线工具的中文关键词推断。报告 UI 自身的 `ResolveReportBackground()` 也按关键词确定颜色，但本轮不改 UI 或报告逻辑。

## 新快照字段

新版 `InspectorReportSnapshots.json` 的 `check.sources` 会保存：

- `checkPipeline`：`IndustrialCircuitRuleAnalyzer` 或 `CircuitRuleChecker.FilterCheckPanelFalsePositives`；
- `pipelineErrorCount`、`pipelineWarningCount`：检查入口的真实计数；
- `pipelineIssueCodes`：家庭/非工业的旧检查器 code；
- `analyzerErrorCount`、`analyzerWarningCount`；
- `validationErrorCount`、`validationWarningCount`、`validationRuleIds`。

原先从中文 block 猜出的 `check.errorCount` / `check.warningCount` 不再生成。block 的 `severity` 保留为展示层辅助信息，不能作为规则 Severity 或错误数量的唯一依据。

`SceneRuntimeEvidenceWindow` 的阶段取证也同步移除了 `errorBlockCount` / `warningBlockCount` 关键词计数，改用同一组真实来源字段。现有 `DemoSceneRuntimeEvidence.json` 仍为旧字段版本，必须在工具编译后重新采集；该文件同时尚缺清空、家庭模板、工业模板、保存并导入四个阶段，暂不提交。

## 重新生成步骤

1. 等 Unity 编译完成后进入 Play Mode；
2. 等默认画布加载完成；
3. 点击 `Tools/Tests/生成架构重构基线`；
4. 等 Console 输出“架构重构基线已生成”；
5. 检查 `Assets/EditorTests/Baselines/V2.3.9.1/ValidationRuleSnapshots.json` 的 `schemaVersion` 为 `2`，并确认两个规则均为 `Warning`；
6. 检查 `InspectorReportSnapshots.json` 已不含旧的 `check.errorCount` 字段，而有 `check.sources`；
7. 点击 `Tools/Tests/验证架构重构基线`。验证前不要手工编辑任何 expected JSON。

新版工具不会自动覆盖失败基线；只有“生成架构重构基线”会在人工明确执行时更新 expected 文件。
