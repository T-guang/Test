# 元件扩展指南

## 扩展检查表

新增元件具有跨层影响。实现前先判断它是纯视觉、纯教学，还是参与电气/运行态行为；再逐项检查：

| 区域 | 必答问题 |
|---|---|
| 定义/目录 | 是否有稳定 `DefinitionId`、展示元数据、参数和端子结构？ |
| 端子语义 | 端子 ID 与角色能否支撑图、规则和模板？ |
| Visual Prefab | 视觉是否匹配定义，并暴露预期 TerminalView？ |
| 元件行为 | 是否需要状态、触点、测量或用户交互？ |
| Analyzer | 能否在不破坏既有元件的前提下推导支持状态？ |
| Runtime | 是否需要计时、保护、运动、互锁或重置语义？ |
| Validation | 是否需要安全/教学规则，以及稳定 RuleId/Severity？ |
| 参数面板 | 是否可展示/编辑而不破坏保存兼容性？ |
| 元件池 | 名称能否直接区分 220V/380V 等变体？ |
| 保存加载 | 必要字段是否可序列化且向后兼容？ |
| 模板 | 若属标准课程内容，是否存在真实 JSON 和目录项？ |
| 测试 | 要补哪些负向、运行态和模板回归？ |

## 建议实施顺序

1. 定义稳定 ID、端子和持久化参数。
2. 构建 Visual Prefab 并核对端子映射。
3. 增加最小工作区生成和持久化支持。
4. 仅在电气行为属于范围时增加 Analyzer/Runtime 支持。
5. 行为明确后再增加 Validation。
6. 增加元件池、参数面板和教学/报告呈现。
7. 最后增加模板和回归覆盖。

## 约束

- 不得用元件池显示文字作为业务 ID。
- 不得让 `CircuitStateAnalyzer` 扫描全场景元件。
- 不得滥用无关 RuleId 来避免新增正确的规则契约。
- 不得绕过真实模板 JSON，改用手摆场景对象。
- 220V/380V 等变体应保持为可区分定义/参数，并在元件池中可读。

电气元件扩展后，应运行两个程序集、相关规则测试、Inspector 模型测试、18 模板基线和一次真实保存加载循环。
